# Спецификация протокола «шифрованный мессенджер»

Версия: 0.1 (черновик). Обозначения проекта: **нейтральное кодовое имя — `VEIL`**.

## 1. Модель угроз

Защищаемся от:
- пассивного наблюдателя канала (провайдер, Wi-Fi): видит зашифрованный поток, не должен определять содержимое, получателей, факт активности (padding + периодичность);
- сервера-ретранслятора: не имеет ключей, не расшифровывает, не хранит метаданные дольше очереди доставки, не логирует IP;
- компрометации сервера: хранение только зашифрованных конвертов, перехваченное не расшифровывается (прямая секретность);
- компрометации устройства в моменте: прямая секретность Double Ratchet — прошлые сообщения не раскрываются.

Не защищаемся (честные границы):
- глобальный активный наблюдатель, коррелирующий тайминги входа/выхода у всех участников (решается onion-маршрутизацией, этап 3);
- изъятие работающего устройства с открытым приложением (локальная БД зашифрована, но ключ в памяти);
- сам пользователь, раскрывающий контент.

## 2. Идентичность

- При первом запуске устройство генерирует:
  - **Ed25519** ключевую пару `IKa / IKp` — подписи и идентичность;
  - **X25519** ключевую пару `EKa / EKp` — согласование (обёртка над IK для X25519-обмена);
  - **Spk** (signed prekey) и пул одноразовых prekey — как в X3DH.
- **ID пользователя** = `Base58( SHA-256(IKp) )[:16]`. Сервер хранит только `H = SHA-256(ID)`.
- **Юзернейм** — необязательная публичная строка `[a-z0-9_]{3,32}`, публикуется сервером вместе с `IKp`; принадлежность подтверждается подписью `IKa`. Изменяемый, удаляемый.
- Телефон / email / имя НЕ собираются никогда. Никаких полей под них в API нет.

## 3. Регистрация и аутентификация

- Регистрация автоматическая при первом запуске: клиент отправляет `{H(ID), IKp, SPK, SPKsig, пул OTK}`.
- Каждый последующий запрос подписывается `IKa` (заголовок `X-Author: base64(sig над (method|path|sha256(body)))`); сервер проверяет sig по сохранённому `IKp`. Пароля на сервере нет, сессийных токенов нет — подпись каждого запроса.
- Устройство хранит приватные ключи в зашифрованном виде (ключ БД, см. §6).

## 4. Сообщения (Double Ratchet)

- Сеанс 1:1 устанавливается по схеме X3DH: инициатор забирает `SPK/OTK` получателя с сервера, выполняет DH-обмен, далее Double Ratchet (цепочки sending/receiving, DH ratchet каждое сообщение в новом направлении).
- Каждый «конверт» для сервера:
  ```
  envelope = {
    to: H(ID получателя),          // серверу только хеш
    from: H(ID отправителя),
    payload: b64( ratchet_ciphertext ),  // непрозрачно для сервера
    pad_len: N                     // паддинг до фиксированных размеров
  }
  ```
- Паддинг: размер payload нормализуется по сетке (256 / 1К / 4К / 16К / 64К / 256К / 1М), недостающее — случайные байты.
- Сервер НЕ расшифровывает, НЕ хранит расшифрованные копии, НЕ хранит историю после доставки.

## 5. Сервер-ретранслятор (уровень 2)

Хранит на пользователя:
- `IKp, SPK, sig, пул OTK` — публичные ключи (перехват безвреден);
- очередь недоставленных конвертов: до доставки, удаляется после подтверждения ACK получателя;
- карту `username -> H(ID)` для поиска.

Запрещено / отсутствует:
- логи IP, User-Agent, таймстемпов привязки к запросам;
- любые бэкапы очередей;
- механизм восстановления аккаунта (его нет ни у кого, включая админа).

API (все запросы подписаны):
- `POST /register`, `POST /prekeys`, `GET /prekeys/{H(ID)}`
- `POST /send` (конверт в очередь), `GET /fetch` (забрать конверты), `POST /ack`
- `GET /lookup/{username}`, `POST /username` (занять/сменить)
- `POST /erase` — **сертификат стирания**: тело = `{H(ID), counter, ts}` подписано `IKa`. Сервер удаляет всё связанное с `H(ID)` немедленно и безвозвратно: ключи, очередь, username. Повторная регистрация с тем же ID невозможна только потому, что ID утекает вместе с ключами — ключи стёрты локально, значит ID мёртв.
- Транспорт: TLS 1.3, HTTP/2; на Android — весь трафик через SOCKS5-прокси (Orbot/Tor) или VPN-режим, опция «Tor-only» (клиент refuse прямых соединений).

## 5.1. Доступность Tor и мостов (жёсткое правило транспорта)

- **Прямых соединений не существует.** Если Tor недоступен — приложение не
  отправляет ничего и показывает инструкцию, как включить мосты. Никаких
  IP-фолбэков: анонимность не торговается на доступность.
- **Мосты (obfs4/Snowflake):**
  - в приложение вшит стартовый набор мостов (регулярно обновляется релизами);
  - клиент умеет подтягивать свежий список мостов с реле (список передаётся
    через зашифрованный канал, без привязки к ID);
  - пользователь может добавить свой мост вручную (obfs4-сертификат);
  - мосты включены по умолчанию — приложение соединяется через них сразу.
- **Пользовательский VPN (VLESS/свой VPN):** если у пользователя включён
  системный VPN, весь трафик Orbot автоматически проходит через него —
  отдельной поддержки не требуется. Дополнительно в настройках клиента есть
  «кастомный SOCKS-прокси» для не-системных VPN-клиентов. Сценарий:
  «Tor не подключился → пользователь включает свой VLESS → повторная попытка».
- Клиент показывает три состояния транспорта: Tor-мосты OK / Tor недоступен
  (рекомендация включить мосты или VPN) / готово.

## 5.2. Шумовой трафик и отсутствие метаданных активности

Цель: анализ трафика (взломанным сервером, провайдером, наблюдателем канала)
не должен определять моменты отправки/получения сообщений и активность.

**Отсутствующие метаданные (по дизайну, не отключаемо):**
- статусы «онлайн / был(а) недавно» — не существуют;
- время захода на сервер — не хранится, не логируется, не отдаётся;
- «прочитано» как серверное событие — отсутствует; чек-марки, если включены,
  передаются внутри обычных зашифрованных конвертов и известны только получателю;
- таймстемпы привязки запросов — запрещены (см. §5).

**Шум (cover traffic) — обязательный слой протокола:**
- клиент в активном режиме шлёт пакеты фиксированного размера с фиксированной
  периодичностью (по умолчанию 1 пакет / 10 сек, настраиваемо); реальное
  сообщение занимает пакет, при отсутствии — пакет случайных байтов;
- сервер в ответ на fetch возвращает смесь реальных и мусорных конвертов,
  чтобы пустой опрос был неотличим от опроса с сообщениями;
- на сервере запрещено отличать шум от сообщений логикой приложения:
  шум создают клиенты, сервер просто пересылает зашифрованные пакеты.

**Честные границы (задокументировано, не скрывается):**
- факт активной сессии (ID в сети сейчас) скрыть невозможно — шум прячет
  моменты отправки, не сам факт подключения;
- постоянный шум повышает нагрузку пропорционально числу пользователей;
  на мобильных устройствах предусмотрены профиль «постоянный шум» и профиль
  «шум при активности» (компромисс батарея/скрытность, выбирает пользователь).

## 6. Локальное хранение (клиент)

- БД — SQLCipher, ключ БД — случайные 32 байта, шифруются ключом из PIN/пароля пользователя (Argon2id) и хранятся только в памяти сессии.
- Пароль НЕ хранится нигде. Забыл пароль без бэкапа ключей = данные утрачены (это фича).
- Приватные ключи IK/SPK — только внутри SQLCipher.
- «Паническое удаление»: стирает файл БД + ключи + кэш с перезаписью, подписывает /erase на сервере.

## 7. Фичи, совместимые с анонимностью

Разрешены (шифруются тем же рatchet-слоем): файлы и медиа (AES-256-GCM ключом сессии, чанками), голосовые, реакции, правка/удаление сообщения, self-destruct (счётчик на получателе, сервер срока жизни не знает), пересылка, поиск по локальной БД.

Не допускаются: облачная история на сервере, публичные каналы с профилями, Web-версия с сессиями на сервере, поля «имя/телефон» в модели данных.

## 8. Звонки

- Сигналинг — через конверты §4 (сервер видит только факт «есть конверт»).
- Медиа — WebRTC с DTLS-SRTP, ключи согласуются через подписанные SDP-конверты end-to-end.
- TURN-серверы при необходимости — доверенные, трафик к ним SRTP-шифрованный; маскировка объёма — padding/постоянный битрейт.

## 9. Этап 3 — onion-маршрутизация

- Сеть узлов ≥ 5; клиент строит цепочку из 3 узлов, многослойное шифрование (каждый узел знает только prev/next).
- Сервер публикуется как onion-сервис ( Tor hidden service) — совместимо с Orbot уже сейчас без своего шага 3.
- Трафик-анализ смягчается: фиксированный битрейт, батчинг, cover traffic.

## 10. Стек

- Сервер: Go 1.22+, без БД (только зашифрованные очереди в памяти + персистентность запрещена).
- Клиент Android: Kotlin, SQLCipher, Conscrypt/LibSodium (через lazy library), Tor via Orbot SOCKS5 (127.0.0.1:9050).
- Криптопримитивы: X25519, Ed25519, HKDF-SHA256, AES-256-GCM, Argon2id. Не изобретаем свои схемы.

## 11. Самостирание при неверном PIN (жёсткое правило)

- PIN по умолчанию: 4 цифры, задаётся при первом запуске.
- 5 неверных попыток подряд → автоматическое безвозвратное стирание:
  - локальная SQLCipher-БД и все ключи уничтожаются;
  - на сервер уходит `POST /erase` по Keystore-токену (32 случайных байта,
    обёрнутых аппаратным ключом Android Keystore; извлечь их из устройства
    нельзя) — аккаунт, очередь, юзернейм удаляются на сервере;
- восстановление невозможно; создаётся только новый аккаунт.
- Граница (честно): локальные копии переписки У СОБЕСЕДНИКОВ остаются на их
  устройствах — центрально стереть их нельзя, не разрушив end-to-end.
  Сессия с удалённым ID умирает (ключи стёрты), новые сообщения невозможны.
